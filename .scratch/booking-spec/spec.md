# Спецификация: Календарь звонков

Источник решений: `GLOSSARY.md`, `AGENTS.md`, ADR `docs/adr/0001`–`0004`, карта `.scratch/booking-spec/map.md` и ответы тикетов 01–11.

## Проблема

Владельцу нужно публиковать типы встреч и принимать бронирования, не разбираясь в календарных инструментах. Гостю нужно по публичной ссылке быстро понять, какие встречи доступны, увидеть только реально свободное время и записаться без регистрации, не столкнувшись с двойной записью на один слот. Сейчас в репозитории есть только лендинг и заглушка страницы записи: нет контракта API, хранения, расписания, бронирований и админки.

## Решение

Учебный сервис онлайн-записи из одной публичной страницы записи и одной админки без авторизации. Владелец настраивает имя и типы встреч, гость выбирает тип, дату и свободный слот в 14-дневном окне, заполняет имя, email и необязательный комментарий и получает подтверждение. Расписание фиксировано: Пн–Пт 09:00–18:00 Europe/Moscow, шаг стартов 30 минут. Занятость глобальна для всех типов и защищена от гонок на уровне SQLite. Архив заменяет удаление типа встречи. Контракт описан в TypeSpec и генерирует OpenAPI, клиентский SDK и серверные типы; релизы автоматизируются release-please после первой сквозной функции.

## Решения по реализации

### Контракт и генерация

- Отдельный workspace `contract/` на TypeSpec 1.18.0; namespace `BookingApi`; источник истины — TypeSpec-файлы.
- Эмитится OpenAPI 3.1.0 в коммитируемый `contract/openapi/openapi.yaml`.
- `@hey-api/openapi-ts` запускается дважды из одного YAML: фронтенд получает Fetch-клиент, SDK и типы; бэкенд — только типы.
- Явные `operationId` для всех операций; сгенерированный TypeScript не коммитится; CI проверяет дрейф OpenAPI.
- Базовый путь `/api` задаётся сервером/`baseUrl` клиента, а не ресурсными путями контракта.

### Данные и схема

- SQLite через `better-sqlite3`, один процесс и одно соединение в первой итерации; WAL, `foreign_keys = ON`, `busy_timeout`.
- Версионные TypeScript-миграции с таблицей `schema_migrations`; миграции применяются при старте и в тестах.
- `owner` — singleton-строка `id = 1` с `display_name`; идемпотентный `ensureOwner`, имя из `OWNER_NAME` или «Владелец».
- `meeting_types`: `id`, `name`, `description`, `duration_min`, nullable `archived_at_ms`.
- `bookings`: `id`, `meeting_type_id`, `start_ms`, `end_ms`, `guest_name`, `guest_email`, nullable `comment`, `created_at_ms`; `CHECK (end_ms > start_ms)`; `ON DELETE RESTRICT`; индексы `(start_ms, end_ms)` и `(meeting_type_id)`; колонки `status` нет.
- Триггеры `BEFORE INSERT/UPDATE` с `RAISE(ABORT, 'booking_overlap')` как backstop против прямого SQL.
- Расписание, часовой пояс, окно 14 дней и шаг 30 минут — константы домена, без таблиц расписания.
- Время в БД — UTC epoch milliseconds; длительность — целые минуты.

### Время, окно и занятость

- Часовой пояс — `Europe/Moscow`; «сегодня» — начало текущих суток в этой зоне; окно — 14 календарных дней со смещениями 0..13.
- В API время — ISO 8601 UTC с `Z`; календарная дата — `YYYY-MM-DD` по Москве; UI форматирует через `Intl` с явной зоной.
- Рабочие дни Пн–Пт, часы 09:00–18:00, старты по сетке `09:00 + n * 30`; валиден слот с `start > now` и `start + duration <= 18:00`.
- В ответе доступности присутствуют все 14 дней, пустые и выходные — с пустым списком слотов.
- Занятость задаётся полуинтервалом `[start, end)` и предикатом `bs < e AND be > s`; примыкание разрешено; занятость глобальна для всех типов.
- Создание брони выполняется в `BEGIN IMMEDIATE`: чтение типа, проверка слота, проверка пересечения и вставка в одной транзакции; при пересечении — конфликт, при `SQLITE_BUSY` — недоступность записи.

### API-контракт

Публичные операции:

- `listPublicMeetingTypes` — активные типы встреч.
- `getAvailability` — доступность на 14 дней для выбранного типа, с типом внутри ответа.
- `createBooking` — создание брони по типу, старту и контактам гостя.

Админские операции (без авторизации, семантическое разделение):

- `getOwner`, `updateOwner` — профиль владельца.
- `listAdminMeetingTypes`, `getAdminMeetingType`, `createMeetingType`, `updateMeetingType` — управление типами.
- `archiveMeetingType`, `restoreMeetingType` — жизненный цикл вместо удаления.
- `listUpcomingBookings` — предстоящие встречи.

Форматы:

- Идентификаторы — положительные `int32`; нечисловой path-id — `400 invalid_request`.
- Поля — `camelCase`; длительность — `durationMin`; время — `utcDateTime`; дата — `plainDate`.
- Создание брони принимает тип, старт, имя, email и необязательный комментарий; `end` и длительность вычисляет сервер.
- Ответ создания брони содержит всё для экрана подтверждения: тип, интервал, владельца, данные гостя, время создания.
- Списки — плоские массивы без пагинации; предстоящие отсортированы по старту, группировка по дате — на клиенте.
- Ошибки — единая модель с `code`, `message` и опциональными `fieldErrors`: `invalid_request` 400, `validation_error` 422, `not_found` 404, `slot_unavailable` 422, `slot_taken` 409, `service_busy` 503, `internal_error` 500.
- Idempotency key, отмена и версионирование URL в первой итерации не вводятся; OpenAPI 3.1.0 без префикса версии; изменения внутри итерации только аддитивные.

### Публичный сценарий гостя

- Одна страница `/book` с прогрессивным раскрытием: тип → дата → слот → форма → подтверждение; прямая ссылка `/book/:meetingTypeId`.
- Выбор даты и слота не кодируется в URL; форма появляется после выбора слота.
- При конфликте и недоступности слота контакты сохраняются, слот сбрасывается, доступность перезапрашивается, другой слот не выбирается автоматически.
- Экран подтверждения показывает тип, длительность, интервал по Москве, имя владельца, данные гостя, пояснение об отсутствии письма и кнопку повторной записи.
- Обязательный минимум доступности: нативные управляемые элементы, видимые подписи, `aria-invalid`/`aria-describedby`, `role="alert"`, live-region, управление фокусом, зоны не меньше 44×44 px, состояние не только цветом.

### Админский сценарий владельца

- Отдельный маршрут `/admin` с постоянным уведомлением о демо-режиме без авторизации.
- Три секции: «Профиль», «Типы встреч», «Предстоящие встречи»; новых библиотек и state-менеджера нет.
- Создание и редактирование типов — inline-форма без модальных окон; название обязательно, описание необязательно, длительность 15..540 минут и кратна 15; дубликаты названий разрешены.
- Архивирование скрывает тип из публичной записи и делает прямую ссылку недоступной; существующие встречи сохраняются; архивный тип read-only; восстановление возвращает тип.
- Предстоящая встреча — с `end > now`, включая идущую; сортировка по старту; группировка по московской дате; бейджи «Сейчас» и «Тип в архиве»; email — ссылка `mailto:`; ручное обновление без polling.
- Занятость владелец видит через список встреч и публичную доступность; отдельного календаря и ручной блокировки нет.

### Конфигурация, эксплуатация и релиз

- Переменные окружения: `DATABASE_PATH` (по умолчанию файл в каталоге данных), `OWNER_NAME`; Node ≥22.18.0.
- Один процесс и одно соединение; горизонтальное масштабирование не обещается.
- Режим durability SQLite остаётся открытым; в первой итерации достаточно настроек по умолчанию.
- Conventional Commits, squash-merge и линт заголовка PR.
- Один корневой релиз `vX.Y.Z` и `CHANGELOG.md`; release-please включается после первой сквозной функции; первый релиз `0.1.0`.
- Релизный PR использует отдельный токен, чтобы запускать обычный CI; мерж ручной; публикации в npm, Docker и деплоя нет.

## Решения по тестированию

- Хороший тест проверяет внешнее поведение через публичный шов, а не внутренние детали. Приоритет — самый высокий доступный шов, новых швов минимум.
- Главный серверный шов — фабрика приложения с инъекцией `db`, `clock`, `config` и Fastify `app.inject`; реальный HTTP-сокет для API-тестов не используется.
- Доменные чистые функции (`buildSlots`, предикат занятости, валидаторы, часы) покрываются unit-тестами с фиксированным `now`.
- UI-страницы тестируются Testing Library по ролям и подписям; сгенерированный SDK мокается, новых UI-зависимостей нет.
- Сквозной сценарий проверяется Playwright против реального Fastify, временной SQLite и Vite с фиксированными часами.
- Контракт проверяется компиляцией TypeSpec, линтом OpenAPI и drift-check в общей команде.
- API-матрица: типы встреч и границы длительности, публичный список без архивных, архив/восстановление, доступность на 14 дней, пустые дни, прошедшие слоты, последние старты, глобальная занятость, примыкание, создание брони, конфликт, недоступный слот, архивный тип, предстоящие встречи, профиль владельца, коды `400/404/409/422/503`.
- Защита от гонок проверяется детерминированным тестом двумя соединениями, тестом worker-thread, прямыми SQL-тестами триггера и `CHECK`.
- Тест с нарушенным правилом: флаг, действующий только в тестовом режиме, отключает прикладную проверку и триггеры; отдельная команда требует, чтобы конфликтная спека упала, доказывая чувствительность теста.
- Время и зона фиксируются инъекцией часов; основные прогоны идут с `TZ=UTC`, дополнительный прогон — с не-московской зоной.
- Локально и в PR: быстрый `check` без браузера и отдельный e2e Chromium. Nightly: Firefox/WebKit, зонная матрица, mutation-тест, stress гонки.
- Глобального порога покрытия и ретраев в PR нет; нестабильный тест чинится или карантинится.
- Существующие тесты главной и заглушки записи — prior art для страничных тестов; API-тестов пока нет, они появляются вместе с первым срезом.

## Вне scope

- Отмена и перенос броней, уведомления (email, SMS, календарные приглашения).
- Несколько владельцев, команды, регистрация и настоящая авторизация.
- Slug и место проведения у типа встречи, оплата, внешние календари и видеосвязь.
- Нерабочие дни, отпуска и произвольное расписание, повторяющиеся встречи.
- Idempotency key повторной отправки.
- Публикация пакетов в npm, Docker, деплой, auto-merge релизов, draft-релизы.
- Нагрузочное и performance-тестирование, визуальная регрессия, mutation-тестирование помимо нарушения правила конфликта.

## Заметки

- Термины — по `GLOSSARY.md`; ключевые слова: владелец, гость, тип встречи, архивный тип встречи, встреча, предстоящая встреча, слот, занятость, конфликт слота, расписание, рабочие часы, окно записи, доступность, бронирование, страница записи.
- ADR: `0001` — гостевая главная, `0002` — react-router-dom, `0003` — plain CSS с токенами, `0004` — архив вместо удаления.
- Первая функция для запуска релизов — сквозной сценарий: владелец создаёт тип → гость видит доступность и бронирует → владелец видит предстоящую встречу.
- Нарезка на вертикальные срезы — в `slices/01`–`slices/08`; граф блокировок без циклов, первый срез — walking skeleton.
- Риски: ручные Fastify-схемы могут разойтись с контрактом (закрывается compile-time тестом), PAT нужно ротировать, SQLite рассчитан на один процесс, точная версия Playwright уточняется при реализации.

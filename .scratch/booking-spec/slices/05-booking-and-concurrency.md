# S05: Бронирование с защитой от гонок и mutation-тестом

**What to build:** Гость выбирает слот, заполняет имя, email и необязательный комментарий и создаёт бронирование. Сервер вычисляет конец встречи из длительности типа и атомарно проверяет пересечение, поэтому два одновременных запроса не могут занять один слот. Успех показывает экран подтверждения; конфликт сохраняет контакты, сбрасывает слот и обновляет доступность. Отдельная команда доказывает, что тест конфликта падает при намеренно отключённом правиле.

**Blocked by:** S02, S03, S04

**Status:** ready-for-agent

- [ ] Схема `bookings` с `CHECK (end_ms > start_ms)`, индексами и триггерами `booking_overlap`; миграция применяется идемпотентно
- [ ] `POST /bookings` принимает тип, старт, имя, email, комментарий; `end` и длительность вычисляются из типа; `BEGIN IMMEDIATE` + `busy_timeout`
- [ ] `201` с полным подтверждением; `409 slot_taken`; `422 slot_unavailable` (прошлое, вне окна, вне сетки, после 18:00); `422 validation_error` с `fieldErrors`; архивный тип `404`; `SQLITE_BUSY` → `503 service_busy`
- [ ] UI: форма появляется после выбора слота; при `409`/`422` контакты сохраняются, слот сбрасывается, доступность перезапрашивается, фокус на alert; экран подтверждения по тикету 06
- [ ] Успешная бронь исчезает из доступности; примыкание разрешено; занятость глобальна
- [ ] Тесты: API через `inject`, детерминированный тест двумя соединениями, worker-thread гонка, прямые SQL-тесты триггера и `CHECK`
- [ ] `TEST_BREAK_OVERLAP` действует только при `NODE_ENV=test`; `mise run test:broken-conflict` требует падения конфликтной спеки; обычный прогон зелёный

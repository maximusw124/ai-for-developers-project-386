# 09: Определить план проверок и тест с нарушенным конфликтом

Type: grilling
Status: resolved
Blocked by: 01, 08

## Question

Каким должен быть план проверок, включая прямые API-тесты, сквозной браузерный сценарий с настоящим сервером и тест с временно нарушенным правилом конфликта?

Решить:

- как `mise run check` объединяет линтер, типы, сборку, юнит-тесты, API-тесты и e2e; что запускается локально и в CI;
- где проходит шов тестирования: Fastify `inject`, реальный HTTP-сервер, Playwright против реального Fastify + SQLite + Vite;
- какие сценарии покрываются прямыми API-тестами: создание типа встречи, доступность, успешное бронирование, конфликт, примыкание, выход за окно, невалидные данные;
- как поднимать изолированную БД для тестов и очищать состояние;
- как устроен тест с временно нарушенным правилом конфликта: через env-флаг, тестовую конфигурацию или временное изменение кода; как доказать, что тест падает при отключённом правиле и проходит при включённом;
- как фиксировать время и часовой пояс, чтобы тесты не зависели от даты запуска;
- какие проверки обязательны в PR и какие могут быть ночными.

Связанные тикеты: «Исследовать конвейер TypeSpec → OpenAPI → openapi-ts → серверные типы», «Согласовать API-контракт в TypeSpec». Формат — `grilling`; при необходимости добавить `research` по Playwright/CI.

## Answer

### Уровни тестов и шов

| Уровень | Инструмент | Шов | Что проверяет |
| --- | --- | --- | --- |
| Unit (домен) | Vitest | чистые функции с инъекцией `now` | `buildSlots`, предикат занятости, валидаторы, `Clock` |
| API/интеграция | Vitest + Fastify `app.inject` | `buildApp({ db, clock, config })` против реального SQLite | роутинг, сериализация, валидация, ошибки, БД, триггеры, гонки |
| UI-компоненты | Vitest + jsdom + Testing Library | мок сгенерированного SDK через `vi.mock` | состояния загрузки/пустоты/ошибок, доступность, сценарий гостя и админки |
| E2E | Playwright (Chromium) | реальный Fastify + временный файл SQLite + Vite на эфемерных портах | сквозной путь гостя и ключевой путь владельца |
| Контракт | TypeSpec + Redocly | `tsp compile` / генерация | отсутствие дрейфа `contract/openapi/openapi.yaml` |

- Основной шов бэкенда — `app.inject`: он проходит через реальный роутинг, сериализацию и валидацию, но не требует портов и не даёт сетевой флаки. Реальный HTTP-сервер отдельно не тестируется.
- E2E используется только для критичных сквозных сценариев, а не для дублирования API-матрицы.
- Базовый путь `/api` живёт в `@server`/`baseUrl` клиента, а не в ресурсных путях контракта.
- Новых UI-зависимостей нет: SDK — обычные функции, которые мокаются напрямую.

### `mise run check`, PR и nightly

- `mise run check:contract`: `tsp compile` → `redocly lint` → генерация SDK/типов для backend и frontend → `git diff --exit-code -- contract/openapi`.
- `mise run check` (локально и в PR, без браузера): `check:contract` → `biome check .` → `npm run typecheck` → `npm run build` → `npm test` с `TZ=UTC`.
- `mise run e2e`: поднимает backend с фиксированными часами и временной БД, Vite на эфемерных портах, запускает Playwright (Chromium).
- `mise run test:broken-conflict`: mutation-проверка правила конфликта (см. ниже); не входит в `check`.
- В PR обязательны `check` и `e2e` (Chromium) отдельными шагами после `npx playwright install --with-deps chromium`.
- Nightly (не блокирует PR): e2e на Firefox и WebKit, прогон с не-московской `TZ`, `test:broken-conflict`, повторный stress-тест гонки.
- Порядок `check` важен: контракт и drift-check первыми, затем линт/типы/сборка, затем тесты.

### Изоляция БД и инъекция зависимостей

- `buildApp({ db, clock, config })` — фабрика; в рантайме аргументы имеют дефолты, в тестах передаются явно.
- Unit/API: новый `better-sqlite3(':memory:')` на тест-файл (или на тест), миграции с нуля, идемпотентный `ensureOwner`, закрытие соединения в `afterEach`. `PRAGMA foreign_keys = ON`.
- Тесты триггеров, двух соединений и worker-thread используют временный файл через `fs.mkdtemp` и удаляют каталог после; для файловой БД — `journal_mode = WAL`.
- E2E: отдельный временный `DATABASE_PATH`, миграции и сид при старте, пересоздание на каждый прогон. Общий dev-файл БД не используется.
- Тестовые флаги (например, нарушение правила конфликта) действуют только при `NODE_ENV=test`; в других режимах выставляются в ошибку на старте.

### Матрица API-сценариев

Прямые API-тесты через `inject`:

- **Типы встреч:** создание `201`; `durationMin` на границах 14/15/45/540/541 и нецелое; пустое имя; необязательное описание; дубликаты названий; `PATCH`; archive/restore; `GET` админский; публичный список без архивных; `404` на неизвестный.
- **Доступность:** ровно 14 дней; выходные и пустые дни с `slots: []`; прошедшие слоты сегодня отброшены; последние старты для 30/45/60/540; глобальная занятость по всем типам; примыкание разрешено; архивный/неизвестный тип `404`; 14-й день присутствует, 15-го нет; полночь MSK не съезжает на UTC-дату.
- **Бронирование:** `201` с полным `BookingConfirmation`; `end` вычисляется из типа, клиентский `end`/`duration` игнорируется; `409 slot_taken`; примыкание `10:00–11:00` + `11:00–11:30` успешно; вне окна/в прошлом/вне сетки/после 18:00 → `422 slot_unavailable`; невалидные поля → `422 validation_error` с `fieldErrors`; архивный тип → `404`; `503 service_busy` при симуляции `SQLITE_BUSY`.
- **Предстоящие встречи:** фильтр `end > now` включая идущую; сортировка по `start`; флаг `archived`; пустое состояние.
- **Владелец:** `GET` и `PATCH`; пустое имя → `422`.
- **Ошибки и backstop:** битый JSON и нечисловой path-id → `400 invalid_request`; прямой SQL-тест триггера (`booking_overlap`) и `CHECK`; детерминированный тест двумя соединениями и worker-thread тест гонки из тикета 04.

### Тест с нарушенным правилом конфликта

- Флаг `TEST_BREAK_OVERLAP=1` принимается только при `NODE_ENV=test`, иначе старт падает с ошибкой.
- Флаг отключает прикладную проверку пересечения и создание overlap-триггеров (опция миграции, доступная только тесту).
- Обычный прогон: конфликтная спека ожидает `409` и проходит.
- `mise run test:broken-conflict` запускает только конфликтную спеку с флагом и **требует, чтобы прогон упал** (инверсия ожидания). Это доказывает, что тест чувствителен к удалению правила.
- Ручное доказательство: с `TEST_BREAK_OVERLAP=1` конфликтная спека красная, без флага — зелёная.
- Проверка живёт в nightly/ручном прогоне, а не в `check`, потому что по определению должна падать.

### Фиксация времени и часового пояса

- Домен получает `Clock { now(): number }`; внутри доменных функций нет `Date.now()`.
- Тесты используют явные инстанты (например, понедельник `2026-11-16T06:00:00Z` = 09:00 MSK) и `vi.setSystemTime`, где нужен таймер.
- Основные прогоны идут с `TZ=UTC`; nightly дополнительно прогоняет с не-московской зоной (`TZ=Pacific/Kiritimati`), чтобы поймать случайное локальное время.
- E2E поднимает backend с тестовым `FIXED_NOW`, чтобы 14-дневное окно было стабильным; реальные часы не используются в ассертах.

### Runtime-валидация на бэкенде

- Используются нативные **Fastify JSON Schema (Ajv)** рядом с роутами; новых зависимостей нет.
- Кастомный `setErrorHandler` мапит:
  - ошибку парсинга JSON (`FST_ERR_CTP_INVALID_JSON_BODY`) → `400 invalid_request`;
  - ошибку схемы (`error.validation`) → `422 validation_error` с `fieldErrors`.
- Контракт остаётся источником истины для типов; добавляется compile-time тест, что ключи ручных схем совпадают с сгенерированными DTO.
- Zod/Valibot в первой итерации не вводятся.

### Покрытие, ретраи и стабильность

- Глобальный порог покрытия не вводится; отчёт покрытия информативный.
- Обязательны именованные критичные спеки: конфликт, примыкание, окно и сетка, часовой пояс, архив, гонка.
- В PR `retries: 0` и `forbidOnly`; нестабильный тест чинится или карантинится с тикетом, а не маскируется ретраями.
- Playwright: `trace: 'retain-on-failure'`; ночные прогоны могут использовать 1 ретрай только для выявления flaky.
- Детерминизм: фиксированные часы, временная БД, эфемерные порты, отсутствие внешней сети.

### Вне scope

- Нагрузочное и performance-тестирование в первой итерации не проводится.
- Точная версия Playwright и конфигурация CI-кэша браузеров — вопрос реализации; при сомнениях уточняется коротким `research`.
- Подключение `check:contract` к реальному конвейеру станет возможно после создания `contract/*.tsp` (реализация тикета 08).
- Порог покрытия, mutation-тестирование помимо нарушения правила конфликта и визуальная регрессия — вне scope.

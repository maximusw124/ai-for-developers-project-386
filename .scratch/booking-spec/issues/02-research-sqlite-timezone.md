# 02: Исследовать SQLite и работу с часовыми поясами на Node 22 и Fastify

Type: research
Status: resolved
Blocked by: —

## Question

Как выбрать SQLite-драйвер и способ работы с часовым поясом для Node 22 + Fastify, чтобы корректно гарантировать непересечение встреч и считать 14-дневное окно?

Ответ должен зафиксировать:

- сравнение `better-sqlite3`, встроенного `node:sqlite` и альтернатив (например, `libsql`) для синхронных транзакций, блокировок и тестируемости на Node 22;
- ограничения нативной сборки на Windows и в GitHub Actions, наличие префиксов и поддержку версий;
- как SQLite гарантирует атомарность проверки пересечения и вставки бронирования при одновременных запросах: режимы транзакций, `BEGIN IMMEDIATE`, индексы, ограничения или триггеры;
- выбор библиотеки для Europe/Moscow: `Intl.DateTimeFormat`, `date-fns-tz`, `Luxon` или `Temporal`, с учётом отсутствия стабильного Temporal в Node 22;
- как считать календарные дни и рабочие часы, не завися от часового пояса сервера, и как тестировать время с фейковыми таймерами;
- ссылки на первичную документацию по каждому утверждению.

Связанные тикеты: «Определить модель данных и схему SQLite», «Зафиксировать правило занятости и защиту от одновременных бронирований», «Зафиксировать 14-дневное окно и генерацию слотов». Формат — `research`; результат сохранить в `.scratch/booking-spec/research/sqlite-timezone.md`.

## Answer

Выбран `better-sqlite3` 13.x: prebuilt-бинарники, WAL, синхронный API и `.immediate()`. Атомарность бронирования — `BEGIN IMMEDIATE` + `busy_timeout` + `SELECT` пересечения по всем типам встреч + `INSERT` в одной транзакции; backstop — `BEFORE INSERT/UPDATE` триггер, `CHECK (end_ms > start_ms)` и индекс `(start_ms, end_ms)`. Время хранится как UTC epoch ms, календарная логика — Luxon с явной зоной `Europe/Moscow`; тесты используют инъекцию часов, fake timers, `TZ=UTC`, а гонка воспроизводится двумя соединениями/worker threads. Полные детали и источники: [sqlite-timezone.md](../research/sqlite-timezone.md).

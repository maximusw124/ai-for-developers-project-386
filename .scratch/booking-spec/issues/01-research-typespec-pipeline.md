# 01: Исследовать конвейер TypeSpec → OpenAPI → openapi-ts → серверные типы

Type: research
Status: resolved
Blocked by: —

## Question

Какой именно конвейер Design First использовать в этом репозитории: TypeSpec → OpenAPI → клиентский SDK для фронтенда и серверные типы/артефакты для бэкенда?

Ответ должен зафиксировать:

- актуальные версии TypeSpec и эмиттера OpenAPI, совместимые с Node 22 и TypeScript 5.6;
- структуру контракта: где лежит `main.tsp`, как описываются модели, операции и ошибки, один файл или несколько;
- точные команды компиляции и проверки, какой файл OpenAPI получается (версия 3.0/3.1) и как он валидируется;
- как `@hey-api/openapi-ts` (или выбранная альтернатива) генерирует клиент, типы и сервисы, и как бэкенд получает типы без импорта из фронтенда;
- где хранить сгенерированные артефакты в монорепозитории, коммитить ли их, как не допустить рассинхронизации в CI;
- какие ссылки на первичную документацию подтверждают каждое утверждение.

Связанные тикеты: «Согласовать API-контракт в TypeSpec», «Определить план проверок и тест с нарушенным конфликтом». Формат — `research`; результат сохранить в `.scratch/booking-spec/research/typespec-pipeline.md` и сослаться из ответа.

## Answer

Выбран отдельный workspace `contract/` с TypeSpec 1.18.0; источник истины — `contract/**/*.tsp`, эмитится OpenAPI 3.1.0 в `contract/openapi/openapi.yaml` и коммитится. `@hey-api/openapi-ts@0.99.0` запускается дважды: фронтенд получает Fetch-клиент, SDK и типы, бэкенд — только типы. Сгенерированный TypeScript не коммитится; CI выполняет compile → redocly lint → generate → typecheck/build → `git diff --exit-code -- contract/openapi`. Требуется Node ≥22.18.0, точная фиксация версии обязательна. Полные детали, команды и источники: [typespec-pipeline.md](../research/typespec-pipeline.md).

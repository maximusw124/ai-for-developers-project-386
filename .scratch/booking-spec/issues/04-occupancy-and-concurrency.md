# 04: Зафиксировать правило занятости и защиту от одновременных бронирований

Type: grilling
Status: resolved
Blocked by: 02, 03

## Question

Как формально определить занятость и гарантировать, что интервалы двух бронирований не пересекаются даже при одновременных запросах?

Решить:

- полуинтервал `[start, end)`: 10:00–11:00 и 11:00–11:30 совместимы, 10:30–11:00 конфликтуют;
- проверка пересечения для всех типов встреч, а не только выбранного;
- атомарная операция «проверить и вставить» в SQLite: транзакция, блокировка, запрос пересечения, индекс; что использовать — ограничение, триггер или сериализацию на уровне приложения;
- поведение при гонке: один запрос создаёт бронирование, второй получает конфликт; какой код и тело ответа;
- что видит гость при конфликте и как обновляются слоты;
- как воспроизвести гонку в тестах и как проверить, что защита действительно работает;
- пограничные случаи: встреча впритык к 18:00, встреча на весь день, нулевая/отрицательная длительность.

Связанные тикеты: «Определить модель данных и схему SQLite», «Зафиксировать 14-дневное окно и генерацию слотов», «Согласовать API-контракт в TypeSpec», «Определить план проверок и тест с нарушенным конфликтом». Формат — `grilling` + `domain-modeling`.

## Answer

### Правило занятости

Встреча занимает полуинтервал `[start_ms, end_ms)`. Для новой брони `[s, e)` и существующей `[bs, be)` пересечение определяется предикатом:

```sql
bs < e AND be > s
```

Следствия:

- `10:00–11:00` и `11:00–11:30` совместимы: `11:00 > 11:00` ложно.
- `10:00–11:00` и `10:30–11:00` конфликтуют.
- Одинаковое начало или одинаковый конец конфликтуют.
- Занятость глобальная: бронирование любого типа встречи блокирует интервал для всех остальных типов.
- Проверка выполняется по всем строкам `bookings`; фильтра по `status` нет, потому что колонки `status` нет.
- При появлении отмен предикат, индекс и триггер должны добавить условие `status = 'confirmed'`.

### Атомарность «проверить и вставить»

Основной механизм — транзакция `BEGIN IMMEDIATE`, а не надежда на синхронность одного процесса:

1. Вызвать `db.transaction(fn).immediate()`: writer-лок берётся до чтения.
2. Внутри транзакции прочитать тип встречи, вычислить `end_ms = start_ms + duration_min * 60000` и проверить бизнес-валидность слота.
3. Выполнить `SELECT 1 FROM bookings WHERE start_ms < @end_ms AND end_ms > @start_ms LIMIT 1`.
4. При пересечении бросить доменную ошибку `SlotTakenError`; транзакция откатывается.
5. Иначе выполнить `INSERT` и закоммитить.

Параметры соединения: `new Database(path, { timeout: 5000 })`, `journal_mode = WAL`, `foreign_keys = ON`. Внутри транзакционной функции не должно быть `await`: `better-sqlite3` не поддерживает асинхронные транзакции.

Отдельный процессный mutex не используется: он защищает только один процесс. Уникальный индекс не подходит, потому что SQLite не умеет exclusion-constraint для интервалов. Deferred-транзакция не подходит: в WAL возможен `SQLITE_BUSY_SNAPSHOT` при попытке записи после чтения.

### Триггеры как backstop

Триггеры включаются в начальную миграцию вместе со схемой:

```sql
CREATE TRIGGER bookings_no_overlap_insert
BEFORE INSERT ON bookings
FOR EACH ROW
WHEN EXISTS (
  SELECT 1 FROM bookings b
  WHERE b.start_ms < NEW.end_ms
    AND b.end_ms > NEW.start_ms
)
BEGIN
  SELECT RAISE(ABORT, 'booking_overlap');
END;

CREATE TRIGGER bookings_no_overlap_update
BEFORE UPDATE OF start_ms, end_ms ON bookings
FOR EACH ROW
WHEN EXISTS (
  SELECT 1 FROM bookings b
  WHERE b.id <> NEW.id
    AND b.start_ms < NEW.end_ms
    AND b.end_ms > NEW.start_ms
)
BEGIN
  SELECT RAISE(ABORT, 'booking_overlap');
END;
```

Триггер — последняя линия защиты от прямого SQL и ошибок в сервисном коде. Основная проверка — прикладная, потому что она позволяет вернуть осмысленный `409`. При `SQLITE_CONSTRAINT_TRIGGER` с сообщением `booking_overlap` ошибка маппится в тот же доменный конфликт.

### Поведение при гонке и HTTP

Из двух одновременных запросов один создаёт бронирование и получает `201 Created`. Второй после ожидания на writer-локе видит закоммиченную первую бронь и получает `409 Conflict`.

Зафиксировано:

- статус — `409`;
- машиночитаемый код — `slot_taken`;
- сообщение — «Это время уже занято. Выберите другой слот»;
- точная структура тела ошибки и имена полей — в единой модели ошибок тикета 08;
- `SQLITE_BUSY` после исчерпания `busy_timeout` — не конфликт слота, а недоступность записи: предлагается `503` с кодом `service_busy` и `Retry-After`; окончательно закрепит тикет 08;
- идемпотентность повторной отправки не вводится: повторный запрос на занятый слот вернёт `409`. Idempotency key остаётся в `Not yet specified`.

Победитель получает `201`, проигравший — `409 slot_taken`. Автоматической записи на другой слот нет.

### Поведение гостя при конфликте

- Имя, email, комментарий и выбранный тип встречи сохраняются.
- Выбранный слот снимается, рядом с выбором времени показывается inline-ошибка.
- Доступность на 14 дней запрашивается заново, слоты перерисовываются.
- Другой слот автоматически не выбирается.
- Фокус переносится на сообщение об ошибке или обновлённый список слотов.
- Повторный выбор занятого слота снова даёт `409`, форма не теряется.

Визуальные состояния и доступность детализирует тикет 06; здесь зафиксирована семантика: данные формы сохраняются, слоты обновляются, автоподстановки нет.

### Валидация и пограничные случаи

- `CHECK (end_ms > start_ms)` — структурная защита от нулевой и отрицательной длительности.
- Доменная валидация до вставки — человеческие ошибки.
- Триггер — защита от пересечений в обход сервиса.

| Случай | Результат |
| --- | --- |
| Встреча заканчивается ровно в 18:00 | Валидна |
| Встреча 09:00–18:00, длительность 540 минут | Валидна, блокирует весь день |
| `end_ms > 18:00` | `422`, слот вне рабочих часов |
| Старт не на 30-минутной сетке | `422` |
| Старт в прошлом или вне 14-дневного окна | `422` |
| `end_ms <= start_ms` | `422`; при прямом SQL — `SQLITE_CONSTRAINT_CHECK` |
| Примыкание `10:00–11:00` + `11:00–11:30` | Обе брони валидны |
| Пересечение с бронью любого типа | `409 slot_taken` |
| Тип встречи не найден | `404` |
| `SQLITE_BUSY` после ожидания | `503 service_busy` |

Точные коды для «вне окна» и «невалидный слот» окончательно согласует тикет 08. Семантически это не `409`: слот не занят, запрос некорректен. Длительность берётся только из типа встречи; клиентское значение длительности не принимается.

### Тесты

- **Детерминированный тест двумя соединениями:** соединение A делает `BEGIN IMMEDIATE`, вставляет бронь и не коммитит; соединение B с `busy_timeout = 100` пытается начать `.immediate()` и получает `SQLITE_BUSY`; A коммитит; B повторяет бронь и получает доменный конфликт.
- **Тест двумя worker threads** с отдельными соединениями и барьером: оба одновременно бронируют один слот; ровно один успех, ровно один конфликт. `Promise.all` в одном потоке гонку не воспроизводит из-за синхронного драйвера.
- **Прямой SQL-тест триггера:** вставить пересекающуюся бронь в обход сервиса и ожидать `SQLITE_CONSTRAINT_TRIGGER` / `booking_overlap`.
- **Тест `CHECK`:** вставить `end_ms <= start_ms` и ожидать `SQLITE_CONSTRAINT_CHECK`.
- **Матрица границ:** примыкание, 18:00, полный день, 17:30 + 60, ноль/отрицательная длительность, прошлое, 14-й день, разные типы встреч.
- **API-тест через `app.inject`:** последовательный конфликт и маппинг в `409`; гонка проверяется на уровне сервиса/БД, а не через HTTP.
- Тест с намеренно отключённым правилом конфликта — зона тикета 09; шов для него — репозиторий/сервис, выполняющий транзакцию.

Обязательны детерминированный тест двумя соединениями, хотя бы один worker-thread тест, тест триггера и тест `CHECK`.

### Операционная модель

В первой итерации предполагается один backend-процесс и одно соединение с SQLite. `BEGIN IMMEDIATE` и `busy_timeout` всё равно используются, чтобы код оставался корректным при появлении второго процесса. Горизонтальное масштабирование не обещается. Режим durability (`synchronous=NORMAL/FULL`) остаётся открытым в `Not yet specified`.

### Глоссарий

- **Занятость** — свойство слота, при котором его интервал пересекается с интервалом существующей встречи; примыкание занятостью не является.
- **Конфликт слота** — попытка забронировать занятый слот, завершающаяся отказом без создания бронирования.

# 07: Спроектировать админский сценарий владельца

Type: grilling
Status: resolved
Blocked by: 03

## Question

Какой должна быть админка владельца без авторизации?

Решить:

- как представлен единственный профиль владельца и как он попадает в систему (сид, конфиг, env);
- маршрут админки и его отношение к публичной странице записи;
- список типов встреч и форма создания/редактирования: id, название, описание, длительность; валидация длительности и границ;
- можно ли удалять тип встречи, если на него есть будущие бронирования; что происходит с формой гостя;
- общий список предстоящих встреч: какие считаются предстоящими, сортировка, какие поля показывать, пустое состояние;
- нужны ли фильтры/пагинация в первой итерации или достаточно одного списка;
- как владелец видит, что слот занят, и как это связано с публичной доступностью.

Связанные тикеты: «Определить модель данных и схему SQLite», «Согласовать API-контракт в TypeSpec». Формат — `grilling` + `domain-modeling`.

## Answer

### Профиль владельца

Владелец остаётся singleton-строкой `owner(id = 1)`. Профиль попадает в систему через идемпотентный `ensureOwner`: при первом запуске имя берётся из `OWNER_NAME`, иначе используется `'Владелец'`. Повторный запуск не перезаписывает уже сохранённое имя, поэтому последующие изменения через админку не зависят от env.

В админке есть секция «Профиль» с одним редактируемым полем «Имя владельца». Имя после trim не может быть пустым; ошибка `422`. Других полей профиля нет: email, аватар, часовой пояс и рабочие часы не редактируются. Расписание показывается как read-only справка: «Пн–Пт, 09:00–18:00, Europe/Moscow». Имя владельца публично и используется на экране подтверждения гостя.

Авторизации нет. На `/admin` постоянно показывается уведомление: «Демо-режим без авторизации: изменения доступны всем, у кого есть ссылка». Это не имитация защиты, а явное предупреждение.

### Маршрут и навигация

- Админка — отдельный маршрут `/admin`.
- Одна страница с тремя секциями: «Профиль», «Типы встреч», «Предстоящие встречи».
- Вложенные маршруты для секций не нужны; достаточно анкорной навигации.
- Публичный header админку не показывает.
- В footer добавляется ссылка «Управление».
- В секции «Для владельца» на главной ссылка ведёт на `/admin` с текстом «Открыть управление».
- В админке есть ссылка «Открыть страницу записи» на `/book`.
- Заголовок документа: «Управление — Календарь звонков».
- Админка использует существующие `SiteLayout`, токены и компоненты; новых библиотек нет.

### Типы встреч: список и форма

Список показывает активные типы выше архивных. Внутри каждой группы порядок по возрастанию `id`. В карточке: название, описание, длительность и действия. ID не редактируется и не показывается как отдельное поле; он используется как ключ и идентификатор для редактирования.

Создание и редактирование выполняются в одной inline-форме без модальных окон:

- название — обязательное, после trim непустое;
- описание — необязательное, может быть пустым;
- длительность — обязательное целое число минут от 15 до 540, кратное 15;
- дубликаты названий не запрещены: `UNIQUE` в БД нет;
- ID не вводится вручную.

Форма показывает ошибки у полей и серверную ошибку в alert. После успешного сохранения список перезапрашивается, показывается success-сообщение, фокус возвращается на заголовок списка. Изменения сразу видны на публичной странице; черновиков и отдельной публикации нет.

При редактировании типа, у которого уже есть бронирования, показывается подсказка: «Изменение длительности повлияет только на новые бронирования». Уже созданные встречи сохраняют свой `end_ms`.

### Архив вместо удаления

Физическое удаление типов встреч не поддерживается. В `meeting_types` добавляется nullable `archived_at_ms INTEGER`; на момент реализации БД ещё нет, поэтому колонка может войти в начальную миграцию, а не отдельным изменением.

Поведение:

- «Архивировать» скрывает тип из публичного списка и делает `/book/:meetingTypeId` недоступным;
- существующие бронирования сохраняются и остаются в списке владельца;
- архивировать можно даже при наличии будущих бронирований; подтверждение предупреждает: «Тип исчезнет из записи, существующие встречи сохранятся»;
- новые бронирования архивного типа невозможны: создание возвращает `404`;
- если гость уже открыл форму и отправляет её после архивации, используется состояние из тикета 06: «Тип встречи больше недоступен» и возврат к выбору типа;
- «Восстановить» снимает `archived_at_ms`, и тип снова появляется в публичной записи;
- архивный тип read-only: редактировать его можно только после восстановления;
- публичные запросы типов и доступности фильтруют `archived_at_ms IS NULL`;
- `/book/:id` для архивного типа показывает существующее состояние «Тип встречи не найден».

`ON DELETE RESTRICT` сохраняется. Отдельный индекс по `archived_at_ms` не добавляется: типов встреч немного.

### Предстоящие встречи

- Предстоящая встреча — встреча с `end_ms > now`; идущая прямо сейчас включается, завершённые не показываются.
- Сортировка по `start_ms` по возрастанию, группировка по московской дате.
- Поля: дата, интервал по Москве, тип встречи, имя гостя, email, комментарий, время создания.
- Email — ссылка `mailto:` с понятным доступным именем.
- Для идущей встречи — бейдж «Сейчас».
- Для встречи архивного типа — бейдж «Тип в архиве».
- Часовой пояс указан текстом: «Время по Москве».
- Пустое состояние: «Предстоящих встреч нет. Когда гости запишутся, встречи появятся здесь».
- Кнопка «Обновить»; polling и автообновление не добавляются.
- Загрузка — скелетоны строк; ошибка — alert с повтором.
- Пагинации и фильтров нет: объём ограничен окном записи и небольшим количеством встреч.

### Занятость и публичная доступность

Отдельного админского календаря и ручной блокировки времени нет. Владелец видит занятость через список предстоящих встреч; ссылка «Открыть страницу записи» показывает публичную доступность, рассчитанную из тех же бронирований. Источник истины — `bookings`; админский список — read-only проекция. Публичная доступность исключает все бронирования; архивный тип в доступности не участвует и возвращает `404`.

### Доступность и состояния

- Все формы имеют видимые `<label>`, `aria-describedby`, `aria-invalid` и `role="alert"` для ошибок.
- Секции образуют последовательную иерархию заголовков; анкорная навигация доступна с клавиатуры.
- Подтверждение архивации — inline, без модального окна; фокус переходит на кнопку подтверждения и возвращается после отмены.
- Success/error сообщения объявляются через live-region.
- Кнопки действий не меньше 44×44 px; статус архивного типа передаётся не только цветом.
- Каждая секция загружается и падает независимо: ошибка типов не скрывает профиль и предстоящие встречи.
- После создания, редактирования, архивации и восстановления списки перезапрашиваются; оптимистичных изменений нет.

### Техническая реализация и тесты

Используется сгенерированный SDK и существующий state-подход без нового state-менеджера. Состояние локально для секций; после мутаций данные перезапрашиваются. Даты форматируются через `Intl` с `Europe/Moscow`. Новых зависимостей нет.

Тесты:

- профиль: загрузка, сохранение, пустое имя, ошибка;
- типы: список, создание, редактирование, границы длительности 14/15/45/540/541 и нецелое значение, дубликаты названий;
- изменение длительности не меняет существующие бронирования;
- архивация с будущими бронированиями и без них, скрытие из публичного списка, `404` на `/book/:id`, сохранение существующих встреч, восстановление;
- отправка гостем формы архивного типа после архивации;
- предстоящие: идущая, будущая и прошедшая встреча, сортировка, группировка, архивный тип, пустое состояние, обновление;
- ошибки загрузки и мутаций с повтором;
- доступность: фокус, подтверждение архивации, live-region.

API-тесты и e2e-детали — тикет 09.

### Глоссарий и ADR

В `GLOSSARY.md` добавляются:

- **Архивный тип встречи** — тип встречи, скрытый из публичной записи; существующие бронирования сохраняются, новые не создаются.
- **Предстоящая встреча** — встреча, интервал которой ещё не закончился, включая идущую сейчас.

Создаётся ADR `docs/adr/0004-archive-meeting-types.md`: архивирование вместо физического удаления меняет жизненный цикл данных и является сознательным выбором между запретом удаления и усложнением модели снимками типа. Прототип не требуется.

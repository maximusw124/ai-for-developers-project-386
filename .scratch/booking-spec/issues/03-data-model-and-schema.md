# 03: Определить модель данных и схему SQLite

Type: grilling
Status: resolved
Blocked by: 02

## Question

Какая модель данных и схема SQLite нужны для владельца по умолчанию, его расписания, типов встреч и бронирований?

Решить:

- состав таблиц и полей: профиль владельца (один), рабочие часы, тип встречи (id, название, описание, длительность), бронирование (слот, тип встречи, гость, контакты, комментарий, время создания, статус);
- как хранить время: UTC-момент, ISO-строка с offset или локальное время плюс пояс; как хранить длительность;
- нужны ли отдельные таблицы для расписания и рабочих часов или достаточно фиксированной конфигурации Пн–Пт 09:00–18:00 Europe/Moscow;
- первичные ключи, уникальные ограничения, индексы под проверку пересечений и список предстоящих встреч;
- подход к миграциям и сидам (владелец по умолчанию, пустой список типов встреч);
- статусы бронирования: только подтверждённые или нужен запас под будущую отмену.

Ответ должен обновить `GLOSSARY.md`, если термины уточняются. Связанные тикеты: «Исследовать SQLite и работу с часовыми поясами», «Зафиксировать правило занятости и защиту от одновременных бронирований», «Спроектировать админский сценарий владельца». Формат — `grilling` + `domain-modeling`.

## Answer

### Владелец и расписание

Один владелец хранится в singleton-таблице `owner` с `id = 1` и отображаемым именем. Отдельных таблиц расписания и рабочих часов нет: в первой итерации расписание фиксировано и задаётся константами домена, а не данными:

- часовой пояс `Europe/Moscow`;
- рабочие дни Пн–Пт;
- рабочие часы 09:00–18:00;
- шаг стартов слотов 30 минут;
- окно 14 календарных дней.

Причина: один владелец, фиксированное расписание и отсутствие админского сценария изменения расписания. Таблица `working_hours` создала бы изменяемую сущность без UI и сценариев. При появлении нескольких владельцев или изменяемого расписания — отдельная миграция и новые таблицы. Часовой пояс не дублируется в БД: единственный источник истины — константа домена.

### Время и длительность

- `start_ms`, `end_ms`, `created_at_ms` — UTC epoch milliseconds в `INTEGER`.
- `duration_min` — целое число минут у типа встречи.
- ISO-строки с offset, локальное время и отдельный часовой пояс в БД не хранятся.
- В API время передаётся как ISO 8601 UTC с `Z`; формат ответа окончательно зафиксирует тикет 08.
- `end_ms` записывается в бронирование при создании. Последующее изменение длительности типа встречи не меняет интервал уже созданной встречи.
- Временные значения передаёт приложение через инъекцию часов, а не SQLite `CURRENT_TIMESTAMP`.

### Схема SQLite

```sql
PRAGMA foreign_keys = ON;

CREATE TABLE owner (
  id           INTEGER PRIMARY KEY CHECK (id = 1),
  display_name TEXT NOT NULL CHECK (length(trim(display_name)) > 0)
);

CREATE TABLE meeting_types (
  id           INTEGER PRIMARY KEY,
  name         TEXT NOT NULL CHECK (length(trim(name)) > 0),
  description  TEXT NOT NULL DEFAULT '',
  duration_min INTEGER NOT NULL CHECK (duration_min > 0 AND duration_min <= 540)
);

CREATE TABLE bookings (
  id              INTEGER PRIMARY KEY,
  meeting_type_id INTEGER NOT NULL REFERENCES meeting_types(id) ON DELETE RESTRICT,
  start_ms        INTEGER NOT NULL,
  end_ms          INTEGER NOT NULL,
  guest_name      TEXT NOT NULL CHECK (length(trim(guest_name)) > 0),
  guest_email     TEXT NOT NULL CHECK (length(trim(guest_email)) > 0),
  comment         TEXT,
  created_at_ms   INTEGER NOT NULL,
  CHECK (end_ms > start_ms)
);

CREATE INDEX idx_bookings_start_end ON bookings (start_ms, end_ms);
CREATE INDEX idx_bookings_meeting_type_id ON bookings (meeting_type_id);
```

Уточнения:

- Первичные ключи — `INTEGER PRIMARY KEY` (rowid), без `AUTOINCREMENT`. Формат id в API (число или строка) решит тикет 08.
- Дополнительных `UNIQUE` ограничений нет. Пересечение интервалов нельзя выразить через `UNIQUE`; правило занятости — тикет 04. Уникальность названия типа встречи, если понадобится, — прикладная валидация тикета 07.
- `description` может быть пустой строкой; `comment` равен `NULL`, если комментарий не указан.
- `duration_min` ограничен `1..540` как проверка здравого смысла. Допустимый набор длительностей утвердит тикет 07; кратность 30 не требуется, так как шаг относится к стартам слотов, а не к длительности.
- `meeting_types` с любыми бронированиями удалить нельзя (`ON DELETE RESTRICT`). Если тикет 07 выберет архивирование, добавим `archived_at_ms` отдельной миграцией.
- Индекс `(start_ms, end_ms)` обслуживает и проверку пересечений, и список предстоящих встреч (`WHERE start_ms >= ? ORDER BY start_ms`). Отдельный индекс по `end_ms` не нужен. Индекс по `meeting_type_id` нужен для FK и выборок по типу.
- Триггер непересечения не входит в решение тикета 03, чтобы не предрешать тикет 04. Схема (`CHECK`, индексы, FK) к нему готова.
- Снимок названия типа встречи в бронировании не хранится: интервал фиксируется в `bookings`, актуальное название берётся из `meeting_types`.

### Статус бронирования

Колонки `status` нет: каждая строка `bookings` — подтверждённое бронирование. Это соответствует определению «Бронирование» в `GLOSSARY.md` и исключает мёртвую фильтрацию. При появлении отмен — отдельная миграция: `status`, `cancelled_at_ms`, частичный индекс `WHERE status = 'confirmed'`, обновление предиката занятости и триггера.

### Миграции и сиды

- Миграции — нумерованные TS-модули с SQL-строками в `backend/src/db/migrations/`, потому что текущая сборка backend — `tsc` без копирования ассетов. `.sql`-файлы потребовали бы отдельного шага сборки.
- Учёт применённых миграций — таблица `schema_migrations (version INTEGER PRIMARY KEY, name TEXT NOT NULL, applied_at_ms INTEGER NOT NULL)`.
- Раннер применяет недостающие версии по порядку. Каждая миграция выполняется в `BEGIN IMMEDIATE`; запись в `schema_migrations` и SQL миграции коммитятся вместе, при ошибке — откат.
- Миграции выполняются при старте приложения и в тестах; тестовая БД — `:memory:`.
- Путь к файлу БД — `DATABASE_PATH`, по умолчанию `backend/data/booking.db`; каталог данных исключается из git.
- Сид владельца идемпотентный и находится вне миграции: `ensureOwner` вставляет `id = 1`, если строки нет; имя берётся из `OWNER_NAME` или `'Владелец'`.
- Список типов встреч сидом не заполняется.
